# Windows TUN 稳定性需求

依据：[排查报告](../../design/windows-tun-disconnect-audit-2026-10-30.md)。用户授权修复桌面安装版断连，并要求严格 SDD 与测试。流程：requirements → design → tasks → implementation → verification。需求编号贯穿实现和验收，未执行的实机测试必须单列。

| ID | EARS 需求 / 验收准则 |
|---|---|
| TS-01 | 当 TCP/channel 缓冲区满或只能部分写入时，适配器应保留未交付字节；恢复消费后双向内容、长度、顺序必须完全一致。 |
| TS-02 | 当应用或远端半关闭时，应在已排队数据之后传递 EOF，并允许反方向继续传输；当握手失败、RST、连接终止时，应释放 SocketSet 和追踪项；正常 FIN 不能因提前释放而丢失。 |
| TS-03 | 当任一方向持续传输时，不应因另一方向 120 秒无应用数据而关闭；当双向均无进展达到 120 秒时，应结束连接且不遗留分离任务。 |
| TS-04 | 当 Windows UAC 启动 TUN 时，桌面端应持有真实进程句柄；只有本次进程发出就绪信号才显示 Running；超时/退出显示 Error，不得假定成功。状态查询应发现运行期退出。 |
| TS-05 | 当用户停止/退出或启动失败时，应针对所管理的 TUN 请求优雅退出并确认结果；失败不得显示 Stopped，不应按映像名误杀其他进程。 |
| TS-06 | 创建 Windows 网卡时应使用配置名称；桌面端应为每次启动启用持久日志，日志有容量上限，保留退出原因；核心任务异常应以失败退出码返回。 |
| TS-07 | 变更应通过针对性测试、原有 TUN/桌面回归与 Windows 编译；报告应区分内存协议栈/localhost 集成与真实 Wintun/UAC 测试，不把编译等同于完整实机验收。 |

本次不改变代理协议、Java/Android 数据面、节点策略，不实现网络切换后的自动路由重建；后者没有用户确认的触发证据，作为后续项保留。源码修复不自动覆盖用户已安装程序。
