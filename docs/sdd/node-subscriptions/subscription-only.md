# 正式线路切换到仅订阅

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| CUT-01 | `zhh-1` 与 `zhh-2` 保持原 UDP 9090。节点强制验证对应设备 CA 签发的有效客户端证书，转发使用该节点的订阅帧密钥。 | 两条公网线路分别通过已授权设备的 TCP、UDP 往返。旧 chacha20 配置和只持有订阅密钥的连接均拒绝。 |
| CUT-02 | 后台分组和设备授权继续生效，切换期间逐台更新。 | 先在回环候选监听验证，再更新公网监听。切换失败可以恢复此前的 systemd 配置。正式用户的设备清单仍包含原节点 ID、地址及端口。 |
| CUT-03 | 桌面新版可以连接正式 HTTPS 订阅入口，并完成浏览器确认、同步和使用。 | Windows 新构建生成配对请求，实际登录确认后显示两条节点。用发布构建产物检查进入订阅流程，额外验证已有代理入口和短期凭证续签。 |
| CUT-04 | 本次提交触发桌面构建，提供可以下载的新版安装包。 | GitHub 构建任务与提交一致，Windows 安装包可下载并校验，macOS 构建结果记录在同一验收表。 |

## 实施顺序

1. 桌面端为专用订阅 API 加载正式入口的公开 CA。系统浏览器沿用其自身的证书信任，并提供复制确认链接给已信任站点的浏览器。既有手动配置保留；同步后对与正式订阅节点地址、端口和传输相同的手动选择改用对应的订阅配置。
2. 提交并推送桌面构建，在发布配置下验证登录与同步。分别检查两台节点的现网进程、当前监听和 TLS 文件，使用已有强制 mTLS 模式启动独立回环候选。
3. 单节点切换使用独立 systemd drop-in 和订阅配置。保留公网反代、节点 ID、节点地址与服务端 TLS 证书。每台在公网通过正反例后继续下一台。后续启动继续使用严格入口。
