# 手动切换改造复盘：如何约束 AI 不过度设计

记录日期：2026-10-21。

这是一份实际开发过程的决策记录。它记录了在 SimplePlanePlatform 加入 HTTP/3 多节点手动切换时，需求方如何通过连续追问、补充约束、要求代码对照和完整验证，将 AI 的实现收敛到必要范围。

本文重点是**如何判断哪些代码有必要生成，以及如何发现并撤回没有必要的扩展**。具体使用与实现细节见 [P1/P2 实现与验证](design/http3-node-selection-p1-p2.md)。

文中的引文来自本次讨论中的用户原话；对动机、方法和工程含义的解释属于事后归纳。提交记录能够确认代码变化，但不等于完整保存了每次讨论，也不能替代具体测试日志。

## 1. 这次任务最初要解决什么

本次目标是支持多个 HTTP/3 节点的配置与手动选择：用户切换节点后，关闭旧节点相关代理连接，新连接使用新节点。

逐步确认的约束包括：

- 先完成 P1、P2；自动故障切换、熔断和恢复探测留到后续阶段。
- 一个节点只需要一条 QUIC 连接，且只连接当前选择的节点，不预先连接备用节点。
- 一条代理流在建立后固定到具体 Invoker，后续 DATA 和 DISCONNECT 沿用原绑定。
- 切换允许旧连接中断，由浏览器或应用重新连接；不迁移既有业务会话，不透明重放业务数据。
- 保留 `ClusterInvoker` 接口与 SPI，为以后扩展选择策略保留位置。
- 沿用现有分层和协议路径，避免顺带重写已经工作的握手、转发与重连逻辑。
- 桌面端原生编译交给 GitHub，代码需要完成本地验证和真实远端链路验证。
- 开发阶段使用独立分支，不直接提交到 main；后续是否合并由当时的明确指令决定。

这里的“不改架构和数据模型”需要准确理解：保留既有分层、SPI 和消息协议，并不意味着完全不能增加字段。本次确实增加了节点 ID、选择配置和流绑定所需的元数据；这些字段直接服务于新能力，没有另建一套通用连接管理架构。

## 2. 最早暴露的问题：实现范围比需求范围更大

AI 最初在实现手动切换时，同时考虑了多连接隔离、连接身份与代次、重连期间的回调归属，以及新的握手缓冲和调度机制。

这些概念都有可以讨论的工程背景，但“概念合理”不能直接推出“本次必须实现”。当时的问题在于，部分机制依赖尚未确认的业务前提，部分机制改变了原有工作路径，却没有先证明它是完成手动切换的必要条件。

范围扩张大致沿着这条路径发生：

```text
增加手动节点切换
  → 同时考虑同节点多连接
  → 增加连接身份、代次与回调区分
  → 调整连接建立和请求调度路径
  → 为新的异步路径增加握手门控与缓存
  → 增加更多状态、清理分支和测试
```

这条路径最值得警惕的地方，是新增机制可能开始为之前的新增机制服务。代码之间形成了一套自洽关系，却逐渐远离原始需求。

用户没有一次性给出全部约束，而是在审查实现时逐步识别并拆除了这些前提。

## 3. 用户是如何一步步收紧范围的

### 3.1 先限制阶段：多节点配置和手动切换先落地

用户先接受分阶段推进：先完成 P1、P2，让客户端能够保存多个节点并选择使用其中一个。

这一选择把“当前交付”与“未来自动故障切换”分开了。自动切换可以影响接口的保留位置，但不应因此要求当前阶段同时实现健康探测、熔断、退避和自动恢复。

**决策作用：先固定当前验收目标，再讨论内部实现。** 否则，只要把未来场景纳入讨论，实现范围就很难结束。

### 3.2 从交付结果追问到底层改动

功能完成后，用户继续问：

> 你这个clientinvoker是改了什么逻辑

> exchangehandler和headexchangehandlerclient修改了什么

> 你这些东西都测试过了是吧

这些追问要求 AI 说明每个改动的职责和依据。仅回答“支持了手动切换”不足以解释为什么底层交换层、入口 Handler 和连接生命周期都发生了变化。

这里逐渐形成了一个审查要求：

> 新增代码必须能沿着“需求 → 职责 → 修改位置 → 验证”解释清楚。

如果一个方法只能解释成“更健壮”“考虑得更全面”，却说不清它在当前模型里解决什么具体问题，就应该继续追问。

### 3.3 追问测试场景，发现“多连接”不是业务要求

AI 曾用下面的测试描述说明连接隔离：

> 连接隔离：关闭 A，只清理 A 的请求和流，B 继续正常

用户追问这是什么场景，随后明确：

> 哦哦哦，但其实我打算一个客户端对远端节点只有1条连接的，是不是可以少不少代码

接着又指出：

> 是的，一个节点只要一条连接，很多代码都不用写了，而且你多条链接的话，客户端初始化的数目够吗，代码里面没看到啊

这一步直接撤销了一个架构前提：当前产品不需要同一节点的连接池、池内调度和多连接实例管理。

它还要求设计与代码相互核对：既然声称支持多连接，就应当能指出这些连接在哪里初始化、如何配置、怎样被选择。没有实际运行路径支撑的设计描述，不能作为继续增加抽象的依据。

**需要保留的区别：** 单节点单连接并不意味着可以不记录资源归属。“关闭 A 不影响 B”的底层隔离测试仍能验证共享注册表的清理边界，但不应据此把“同时管理同节点多连接”变成产品能力。最终手动模式只保持当前节点的一条连接。

### 3.4 明确指出复杂机制，并要求先解释精简方案

用户进一步指出：

> 我觉得很多有点太钻牛角尖了，考虑了很多复杂且没有必要的东西，你像这个监听器，清理对应invoker连接都是必要的，什么进行重连和迟到回调的区分这些我都觉得匪夷所思，你能精简代码吗，在完成功能的基础上少一些过度设计

这里已经给出了一个重要区分：

| 机制 | 当时的判断 |
| --- | --- |
| 接收配置变更的监听器 | 新功能需要保留 |
| 按 Invoker 归属清理资源 | 新功能需要保留 |
| 专门的连接身份、代次管理 | 在当前单连接模型下重新审查必要性 |
| 为未来场景建立更多状态和分支 | 没有当前需求或故障证据时延后 |

用户随后要求：

> 你先把你想要精简什么告诉我

这避免了 AI 把“精简”再次自行解释成另一次大重构。讨论先明确要删除哪些机制、保留哪些职责，再进行修改。

这里的确认用于校准已经发生偏移的实现边界，并不意味着以后每一个普通实现细节都需要反复请求许可。边界明确后，AI 应继续自主完成必要工作。

### 3.5 保留 ClusterInvoker，防止精简破坏合理扩展点

用户明确说：

> clusterinvoker肯定还是要保留的啊，之后自动切换还需要用呢

这一步非常关键。用户要求删除不需要的实现负担，同时保留已有架构中的策略入口。

最终原则是：

- 保留 `ClusterInvoker` 接口与 SPI。
- 当前只实现手动选择和流的固定绑定。
- 将来的自动策略仍可接入这个位置。
- 健康探测、熔断和恢复策略等实现留到其对应阶段。

**接口保留有明确的职责依据；未来机制提前实现则需要额外的当前证据。** 两者应分别判断。

### 3.6 用户亲自把需求压缩成一条闭合链路

在多次讨论后，用户给出了本次最重要的一段边界描述：

> 我们当前这个改动反正就是把stream跟每个invoker绑定上，invoker要跟这个nodeid绑定上，配置变化的时候，监听器收到然后更新clusterinvokers中的配置，同时根据nodeid找到invoker，断掉invoker所持有的所有连接，这一步需要exchangeclient和exchangehandler里面的函数方法来实现，就是如此

这段话同时明确了：

1. **身份关系**：stream 属于具体 Invoker，Invoker 对应稳定 nodeId。
2. **触发来源**：配置变化由监听器接收。
3. **选择更新位置**：集群入口更新可用 Invoker。
4. **清理入口**：根据旧节点找到它的 Invoker。
5. **资源释放边界**：沿既有 Exchange/Transport 链路关闭连接和所属流。

它没有规定所有方法名，却足以约束主要实现。后续每一个新增机制，都应当能说明自己在这条链路中的位置。

如果删除某个新增机制后，这条链路仍然完整，而且必要测试仍然通过，就有充分理由继续检查该机制是否应该存在。

### 3.7 逐方法追问，暴露与切换无关的握手门控

用户继续追问 Exchange 层中哪些方法真正用于关闭连接，并具体贴出了：

```java
deferDownstream(long streamId)
activateDownstream(long streamId)
setStreamClosedListener(LongConsumer listener)
trackStream(long streamId)
abandonConnect(long streamId)
```

这些方法虽然都与流生命周期有关，但职责并不相同：

- `setStreamClosedListener` 对应资源结束后的绑定清理通知。
- `deferDownstream`、`activateDownstream` 和 `DownstreamGate` 属于额外的下行门控、缓存与交付时序机制。
- `trackStream`、`abandonConnect` 是当时具体实现中的辅助入口，不能因为名字包含 stream 或 close 就自动视为必需。

用户随即指出：

> 不是，之前我写的时候可没有这个问题啊，在有切换这个版本之前我们从来没遇到过这个相关的问题，你在这个版本为什么要加进去

这一追问把论证责任转回给了新增代码：必须证明是新需求引入了问题，还是 AI 改变原路径后才需要更多补偿代码。

“之前没有遇到”本身不能证明问题永远不存在，但足以要求提供复现、差异分析或明确的不变量依据，不能直接用假设扩张改造范围。

### 3.8 要求回看改造前版本，用基线约束实现

用户最后要求：

> 对啊，你立刻看看上一个版本的提交，就是没有进行手动切换之前的最新版本的代码逻辑，我一直跟你说要精简，只完成新功能相关的就可以了，不要掺和其他无关的，立刻开始深刻地观看反思，告诉我最精简的，最小改动并且能顺利完成新功能的改造路线

基线对照让讨论从“听起来是否合理”转向了可检查的差异：

- 原版本在哪里完成浏览器握手？
- 原版本怎样发送 CONNECT、DATA 和 DISCONNECT？
- 新功能是否真的要求修改这些路径？
- 原有关闭入口能否复用？
- 能否恢复旧实现，只补上归属和配置切换？

最终精简版本 `60b1fee` 中，以下三个文件与基线 `ef91d0d` 内容一致：

- `HttpConnectHandler.java`
- `Socks5ConnectHandler.java`
- `Http3Client.java`

这给出了一个非常具体的结果：手动切换可以在保留旧入口握手、转发和 HTTP/3 Client 路径的条件下完成。

### 3.9 精简之后仍要求完整测试和真实部署

用户一直强调：

> 写完提交推送到远程那个分支就可以了，1080有代理端口，一定要全链路测试完整了，记得，然后不必要的代码就不要写，省的到时候看不懂

随后继续要求远端全链路测试、性能对比，并提供第二台服务器验证真实跨机切换。

代码是否必要和验证是否充分，是两条独立约束。减少产品状态和分支后，应使用测试证明该实现仍然满足目标行为，不能把验证一起缩减掉。

## 4. 最终收敛后的实现是什么

### 4.1 请求路径保持原分层

```mermaid
flowchart LR
    Browser[浏览器或应用] --> Handler[既有 HTTP CONNECT / SOCKS5 入口]
    Handler --> Cluster[ClusterInvoker：CONNECT 时选择并绑定]
    Cluster --> Filters[原节点 Filter 链]
    Filters --> Invoker[ClientInvoker：持有 nodeId]
    Invoker --> Exchange[ExchangeClient / ExchangeHandler]
    Exchange --> Transport[当前节点的一条 QUIC 连接]
```

绑定保存的是原先选中的具体 Invoker；实际请求仍可经过节点原有 Filter 链。控制器单独保存原始 `ClientInvoker`，用于定位和关闭连接，避免把 Filter 包装对象强制转换成连接持有者。

### 4.2 手动切换流程

```text
外部配置发生变化
  → 监听器读取并校验配置
  → 判断是否影响当前节点连接
  → 暂停向旧选择接纳新流
  → 对原绑定发送 DISCONNECT
  → 有界等待清理确认
  → 关闭旧 ClientInvoker 持有的 ExchangeClient
  → 清理所属控制请求、流和浏览器连接
  → 按新配置建立所选节点的一条连接
  → 更新集群入口与运行状态
```

这比“把节点列表换一下”多了资源归属与关闭过程，但没有要求为浏览器入口增加一套新的调度和握手框架。

### 4.3 职责与必要改动

| 位置 | 最终职责 | 为什么属于本次必要范围 |
| --- | --- | --- |
| 节点配置 | 保存稳定 nodeId、候选节点和当前选择 | 用户需要明确选择某个节点 |
| 配置监听器 | 发现、校验并应用变化 | 保存文件后运行中的代理需要接收变更 |
| `Http3NodeController` | 管理当前节点对应的 ClientInvoker，协调切换和关闭 | 配置选择需要落实为实际连接生命周期 |
| `StickyClusterInvoker` | CONNECT 时绑定；DATA/DISCONNECT 使用原绑定 | 一条流不能在不同节点间逐包改投 |
| `ClientInvoker` | 增加 nodeId，委托原 ExchangeClient 关闭 | 需要从逻辑节点找到实际资源持有者 |
| `ExchangeHandler` | 补充所属流记录与整连接关闭通知 | 关闭隧道时，需要释放它所拥有的流与绑定 |
| `HeaderExchangeClient` | 转接关闭监听，复用已有 close 路径 | 让上层清理与既有资源释放链衔接 |
| 页面与状态文件 | 区分已保存、已应用和节点不可用 | 文件保存成功不代表连接已经成功 |
| TUN 候选节点豁免 | 为所有候选节点地址保留直连路径 | 切换后新节点的隧道流量不能被重新送进 TUN |

`HeaderExchangeClient.close()` 本身已经存在，原路径会调用 Handler 的断开处理并关闭底层 Client。不能把这次所有关闭能力都描述成“新增了一套关闭机制”。

## 5. 最终删除、保留与延后的机制

| 机制 | 决策 | 判断依据 |
| --- | --- | --- |
| 同节点多连接、连接池内选择 | 删除本次相关扩展 | 用户明确一节点一连接，初始化和产品配置也应与此一致 |
| 额外 UUID、连接代次等身份管理 | 精简 | 当前模型可利用 nodeId、具体对象和流绑定表达必要归属 |
| `ClusterInvoker` 与 SPI | 保留 | 原有策略扩展点有明确职责，后续自动策略可复用 |
| stream 与具体 Invoker 的绑定 | 保留 | 保证后续消息仍使用原连接与节点 |
| 配置监听与所属资源关闭通知 | 保留 | 直接服务于热切换与资源回收 |
| `DownstreamGate`、defer/activate 和额外下行缓存 | 删除 | 恢复旧握手路径后，无需由本次切换引入这些补偿机制 |
| 额外 CONNECT 队列、信号量和预算透传 | 删除 | 当前连接可由启动和配置应用线程建立，请求继续使用原路径 |
| 为切换重写 HTTP CONNECT/SOCKS5 Handler | 撤回 | 基线实现可继续承担入口协议职责 |
| HTTP/3 Client 的原有重连实现 | 沿用基线 | 单连接手动选择没有证明需要改写原重连路径 |
| 有界等待 DISCONNECT 确认 | 保留 | 确保远端有机会释放会话，再关闭隧道；同时避免无限等待 |
| DISCONNECT 携带原目标地址和端口 | 保留 | 旧 Filter 链会使用目标信息；缺失这些字段会破坏清理请求 |
| 自动切换、熔断、恢复探测和主动重试策略 | 延后 | 属于 P3，当前没有要求交付 |

精简不是按代码名称分类。例如，监听器不天然复杂，状态字段也不天然多余。判断依据是它所维护的不变量、现有机制能否表达，以及当前需求是否真的需要。

### 5.1 关于迟到回调：需要准确描述最终结果

本次删除了专门扩张出来的身份与代次管理，最终实现仍保留了简单的有效性检查：CONNECT 完成时，检查绑定表中是否还是原来的绑定；已经移除的绑定不能重新变成活跃流。

因此，不能把复盘写成“异步回调一律不用考虑”。这里体现的是：**先用现有对象和绑定关系保护当前不变量，有证据证明不足时，再增加新的身份或状态机制。**

同样，绑定中仍保留了建流是否完成的状态，用于阻止未建好连接就发送 DATA。它直接决定当前请求能否合法执行，属于必要状态。

### 5.2 两次被证据支持的必要修补

资源关闭过程还保留了两项有具体路径依据的修补：

1. 发送 DISCONNECT 后有界等待确认，再关闭 QUIC/UDP 传输，让远端会话能及时收到清理消息。
2. 使用原目标 host、port 构造 DISCONNECT，使它能通过既有 Filter 链；空目标并不是有效的“更简单实现”。

它们增加了少量代码，但能明确指出缺失后哪条路径会失败，因而通过了“必要性”审查。

## 7. 验证怎样为精简提供依据

### 7.1 各层分别证明什么

| 验证层次 | 需要证明的事情 | 不能由它直接证明的事情 |
| --- | --- | --- |
| 集群绑定测试 | CONNECT 后固定归属，DATA 不改投，结束后不能复活 | 真实浏览器握手一定正常 |
| Exchange 生命周期测试 | 整连接结束时只处理所属请求和流 | 整个产品需要同节点多连接 |
| 本地真实 QUIC 集成测试 | 实际传输、分片和会话回收正确 | 公网证书与部署配置一定正确 |
| 独立 Java 进程测试 | main 启动、配置热加载、状态文件和代理协议可串通 | 桌面原生安装包已编译成功 |
| 页面冒烟 | 真实 JavaScript 的选择、保存和参数保留正常 | 原生 IPC、操作系统设置和打包资源都已验证 |
| GitHub 原生构建 | 桌面代码和资源能够编译、打包 | 用户电脑上已经运行了该安装包 |
| 两台真实服务器测试 | 实际跨机切换、旧连接关闭、新请求到达另一节点 | 长期稳定性、峰值容量或所有业务网站兼容性 |

### 7.2 本次留下的验收记录

最终精简版本的实现说明记录：Java 完整 verify 共 192 项，189 通过、3 项条件跳过；10 类生命周期场景各循环 8 次并回到零资源基线；Dashboard 29 项通过，页面和新 JAR 冒烟通过。外部百度站点依赖测试不在这组确定性验证范围内。

后续验证分两步扩大：先在同一公网远端上使用两个逻辑节点 ID，验证配置切换；再引入第二台服务器，完成 A→B→A→B→A 的真实切换。后者每次保持 3 条旧浏览器连接，检查旧连接关闭，以及新连接取得另一台服务器的独立响应标识。

这两个阶段不能混为一谈：两个逻辑 ID 指向同一个端点，能够验证选择逻辑，却不能单独证明两台机器之间的网络路径和部署配置都正确。

### 7.3 性能结果也要遵守证据边界

短时公网测试中，建立连接和小包延迟较接近，吞吐却明显受顺序和网络波动影响，部分轮次的快慢关系发生反转。

这些数据可以作为观测记录，不能被概括成“新版一定更快”或“已经证明完全没有性能退化”。同样，短时 RSS 数值不能直接证明不存在长期泄漏。

本次还留下了“HTTP 响应正文完成后，EOF 关闭时机需要进一步定位”的独立观察。它不应在精简时被掩盖，也不能在没有证据时被重新用来要求手动切换顺带重写整条协议路径。

## 8. 这次 AI 过度设计的具体机制

### 8.1 把未确认的前提当成了既定能力

“有多个候选节点”被扩展成了“需要管理节点内部的多条连接”。后者并不由前者自然推出。用户明确一节点一连接后，相应实现应随前提一起撤回。

### 8.2 把理论可能性直接转换为产品代码

重连、迟到回调、提前到达的数据都有真实技术背景。但需要继续问：原代码是否已经处理？本次差异是否引入了新的失败窗口？有没有复现？能否通过现有绑定关系处理？

缺少这些检查时，AI 很容易把掌握的知识转换成额外机制，造成“考虑得越多，改动越大”。

### 8.3 修改原路径后，又为新路径补偿

如果新增异步入口改变了原握手时序，再增加下行门控和缓存来修复新时序，内部逻辑可能越来越完整，但这并不证明最初改变原路径是必要的。

此时应该回到第一处偏离基线的修改，检查能否保留原路径。逐层修补自己引入的复杂度，未必比撤回最早那一步更合适。

### 8.4 用测试叙事替代需求确认

一个测试能写出来、能通过，不代表它描述的拓扑就是产品需求。用户对“关闭 A、B 继续工作”的追问，揭示了测试场景和实际连接模型之间的区别。

测试应当从已确认的行为约束推导，而不能把为了实现某套抽象写出的测试，反过来当成保留抽象的理由。

### 8.5 用未来扩展给当前成本背书

保留 `ClusterInvoker` 是沿用既有职责边界。提前构建 P3 的运行机制则会立即带来状态、分支、理解和验证成本。这些成本需要由当前需求或明确的近期演进要求承担。

## 9. 用户采用的约束方法，为什么有效

| 方法 | 本次具体做法 | 作用 |
| --- | --- | --- |
| 限定交付阶段 | 先 P1/P2，P3 延后 | 为实现范围提供结束条件 |
| 固定运行模型 | 一节点一连接，只连接所选节点 | 删除不成立的状态空间 |
| 追问修改位置 | ClientInvoker、ExchangeHandler 各改了什么 | 要求代码与需求建立对应关系 |
| 追问场景来源 | “连接隔离是什么场景” | 检查测试是否擅自扩大产品模型 |
| 明确保留项 | 监听、按归属清理、ClusterInvoker | 避免精简破坏必要能力与扩展点 |
| 要求先解释删什么 | 审查精简路线后再实施 | 防止“精简”被解释成新的大改造 |
| 亲自写出闭合流程 | stream → Invoker → nodeId → 配置变更 → 关闭 | 给新增代码提供判断基准 |
| 指定旧提交对照 | 回看 `ef91d0d` | 用可验证的历史实现限制推测 |
| 要求全链路测试 | 本地、独立进程、真实双服务器 | 为删除机制后的行为提供证据 |

这里值得保留的能力，是对业务约束和实现必要性的判断。与成熟项目比较可以提供问题线索，但不能代替对当前产品模型、代码路径和验收行为的独立判断。

## 10. 后续让 AI 生成必要代码的工作方法

### 10.1 开始实现前，先给出四样东西

1. **当前交付行为**：用户进行什么操作，系统必须产生什么可观察结果。
2. **明确运行约束**：例如每节点一连接、只连所选节点、旧流允许中断。
3. **不可改变的既有行为**：例如消息格式、入口握手、DATA 转发与已有 SPI。
4. **验收路径**：如何从用户入口一路验证到远端目标与资源回收。

这些信息比“写得简单一点”“不要过度设计”更容易落实到代码。

### 10.2 对每个新增机制做必要性审查

| 问题 | 应当得到的回答 |
| --- | --- |
| 它服务哪条当前需求？ | 能指到已确认的行为，而不是笼统说健壮性 |
| 它保护哪个不变量？ | 能明确说明哪类错误将被阻止 |
| 原实现哪里不足？ | 给出调用路径、代码差异或可复现案例 |
| 能否复用原字段、对象或方法？ | 先解释现有机制为何不够，再新增一套机制 |
| 删除它会怎样失败？ | 给出具体行为或有意义的测试，而不是“可能有风险” |
| 它增加了什么成本？ | 状态、线程、队列、缓存、接口和运维成本分别是什么 |
| 它是否只服务未来阶段？ | 明确保留接口还是提前交付完整实现 |

这不要求为每一行普通代码写长篇论证。重点审查会扩大状态空间、改变旧路径或增加公共接口的机制。

### 10.3 审查差异时，同时做两个方向的检查

**向上追需求：** 这个修改是否能追溯到已确认需求或已复现故障？

**向下追资源：** 这段代码创建、持有、转移和释放的实际资源是什么？关闭入口在哪里，原实现能否承担？

只做前一个检查，容易遗漏清理；只做后一个检查，容易把资源管理扩张成新的通用框架。

### 10.4 扩大范围时先说明依据

如果实现中发现确实需要改变旧握手、增加队列或引入代次，应先说明：

- 哪个当前场景已经失败，怎样复现。
- 基线为什么无法满足新需求。
- 最小修改是什么，替代方案的代价是什么。
- 影响哪些原有行为，以及如何回归。

边界明确后继续推进实现和验证，不要把“防止过度设计”变成每一个可逆操作都要请求确认的新负担。

### 10.5 完成后交付可核对的结果

至少说明修改位置、保留行为、验证范围、未覆盖边界，以及代码提交和实际运行版本。声称删除了哪些机制，应能从差异中直接找到；声称恢复基线，应能给出对照文件与提交。

## 13. 后续证书问题带来的另一条教训

手动切换通过真实链路测试后，用户在实际桌面端仍遇到了新节点无法使用的问题：新节点沿用了旧节点的服务器名称和独立自签名证书，客户端握手报 `CERTIFICATE_VERIFY_FAILED`。

这属于节点接入和实际配置问题，不能直接据此认定前面的流绑定与切换算法失效。后续修补也采用了明确范围：桌面端暴露每节点 TLS 名称与证书导入，复制公开证书到应用目录，保留现有配置模型，并让空名称按当前 Host 生成 Java 配置。对应提交为 `2ade581`。

此外，从文件侧修正配置后，运行中的旧页面仍可能保留旧值，下一次保存又把文件覆盖。于是，“配置文件已修正”“当前进程已应用”“页面已重新读取”和“新安装包已安装”必须分别验证。

这里补充了对 AI 交付的另一条约束：**既要证明代码机制必要，也要确认用户实际操作链路已经具备使用它的条件。** 代码提交、构建成功、安装完成和当前运行生效，是不同的事实。

这也说明界面改动需要按需求重新判断：手动切换阶段不必顺带扩充 TLS 表单；当实际接入失败已经证明用户无法完成必要配置时，补齐证书操作就有了明确依据。
