# TLS 安全现状与生产改进方案

审计日期：2026-10-22。本文依据当前仓库代码、配置和内置公开证书整理；没有连接线上服务器核验实际握手证书。本文记录现状与整改计划，不代表相关漏洞已修复。

## 1. 结论与范围

当前默认 HTTP/3 节点采用自签证书并由客户端预置信任，旧部署还将 CA 证书直接用作服务端叶子证书。Rust 为此增加了跳过部分标准验证的兼容逻辑。此外，Java 和 Rust 的 HTTP/2 客户端在启用 TLS 时存在关闭身份验证的问题。

这些问题涉及代理节点之间的 HTTP/2、HTTP/3 传输，不能据此认定项目所有 HTTPS 页面或目标网站的 TLS 都存在相同问题。TLS 加密仍可能存在，但服务端身份验证的保障不完整。能否进一步解密代理业务数据，取决于应用层加密、密钥管理和具体攻击路径，不能直接断言所有业务明文均已暴露。

自签证书和私有 CA 本身可以规范使用；本项目需要整改的是 CA 与叶子证书角色混用、过期证书、验证绕过以及缺少可追溯的签发和续期流程。

## 2. 当前实现与证据

### 2.1 内置证书

以下两个文件的 SHA-256 相同，内容为同一张公开证书：

- `proxy-local/src/main/resources/http3-remote-ca.crt`
- `android-app/app/src/main/assets/http3-remote-ca.crt`

| 字段 | 仓库内证书的值 |
| --- | --- |
| Subject | `CN=54.172.101.190` |
| Issuer | `CN=54.172.101.190` |
| SAN | `IP Address=54.172.101.190` |
| Basic Constraints | `CA=true` |
| 有效期 | 北京时间 2026-09-10 17:38:15 至 2026-10-10 17:38:15 |
| 文件 SHA-256 | `306D9984A4D352140A21B39A488D50C0EA5C2140D97586D9AD7320C53CA2CC26` |

截至审计日期，这张内置证书已经过期。其主体和签发者相同，结合代码中对旧部署的说明，可确认项目采用过自签 CA 直接充当服务端证书的方式。线上是否仍使用这张证书，需要另行核实。

当前关系实际是“客户端直接信任的 CA 证书 = 服务端出示的证书”，没有独立的中间 CA 和叶子证书。不能将其描述为存在三层完整证书链。

### 2.2 证书来源与服务端加载

`proxy-remote/src/main/resources/remote.yml` 的 HTTP/3 配置指向：

```yaml
http3:
  certificateFile: /etc/simpleplane/tls/fullchain.pem
  privateKeyFile: /etc/simpleplane/tls/privkey.pem
```

`proxy-transport-http3/src/main/java/com/proxy/transport/http3/Http3Server.java` 的 `createServerSslContext()` 检查路径和文件是否存在，然后交给 Netty 加载。服务端本身不在这里生成证书；文件名 `fullchain.pem` 也不能证明文件包含完整、有效的中间证书链。

本次检查的部署脚本、配置和文档中未找到生产证书的完整签发、续期及轮换流程，因此无法仅凭仓库还原最初的生成命令、操作人或当前线上证书来源。测试代码中的临时证书生成逻辑不属于生产签发流程。

### 2.3 Java HTTP/3 客户端

`proxy-local/src/main/resources/proxy.yml` 默认配置使用上述 IP、`serverName` 和内置 `caFile`，`certificatePin` 为空。

`proxy-transport-http3/src/main/java/com/proxy/transport/http3/Http3Connection.java`：

- 设置 `endpointIdentificationAlgorithm("HTTPS")`。
- 配置 `caFile` 时将文件中的证书作为自定义信任来源；不配置时采用默认信任来源。
- `PinningTrustManager` 先委托标准信任管理器验证，再按配置校验 SPKI 指纹。指纹不是标准校验失败后的通行证。

因此不能把 Java HTTP/3 与 HTTP/2 的无条件信任逻辑混为一谈，也不能保证 Java 客户端会接受已过期的内置证书。

### 2.4 Rust HTTP/3 客户端

`plane-core/src/outbound_h3.rs` 的 `PinnedServerCertVerifier` 注释明确说明：旧部署把自签 CA 当作服务端证书，标准 WebPKI 校验会因 `CaUsedAsEndEntity` 拒绝。

其实际行为是先做标准校验；若失败，只要服务端叶子证书 DER 与配置中的任一证书完全相同，就返回验证成功。该回退没有限定失败类型，因此也可能放过过期、名称不匹配等验证失败。

这条路径仍验证 TLS 握手签名，攻击者不能仅凭拿到公开证书就完成冒充；但它绕过了标准证书策略，证书过期也无法可靠终止信任。

`android-app/app/src/main/java/com/proxy/android/PlaneVpnService.kt` 会在默认 HTTP/3 主机且用户未提供 `caPem` 时注入内置证书。其他节点不自动使用此证书。Rust 未配置自定义 PEM 时使用 `webpki_roots` 提供的公共根集合，不应将其简单称为实时读取操作系统信任库。

### 2.5 HTTP/2 客户端

| 实现 | 证据位置 | 当前行为 |
| --- | --- | --- |
| Java | `proxy-transport-netty/src/main/java/com/proxy/transport/netty/conn/Http2Connection.java`，`initSslContext()` | 使用 `InsecureTrustManagerFactory.INSTANCE`，不验证证书信任链 |
| Rust | `plane-core/src/dispatcher.rs`，`connect_tls()` / `NoCertificateVerification` | 证书验证及 TLS 1.2、1.3 握手签名验证直接返回成功 |

上述问题在相应 TLS 路径被启用时适用。部分示例配置使用 `ssl: false`，这种情况下该 HTTP/2 连接本身没有 TLS，不能将应用层加密等同于 HTTPS 的身份验证。

## 3. 风险与整改优先级

以下为工程整改优先级，不是经过完整攻击验证的 CVSS 评级。

| 优先级 | 问题 | 影响及前提 |
| --- | --- | --- |
| P0 | HTTP/2 跳过服务端身份验证 | 攻击者能够控制路由、DNS 或处于通信路径上时，有机会冒充节点或建立中间人连接；应用层数据影响需另外评估 |
| P0 | Rust HTTP/3 在标准验证失败后按证书相同放行 | 削弱有效期、名称和证书用途限制；私钥泄露后不能依靠过期结束该兼容路径的信任 |
| P1 | CA 与叶子角色混用 | 不兼容标准验证；若同一 CA 私钥部署在服务端且被窃取，可能影响所有信任该 CA 的客户端 |
| P1 | 内置证书过期与更新依赖客户端发布 | 严格验证的客户端可能拒绝连接，兼容客户端与严格客户端行为不一致 |
| P1 | 签发、续期、轮换流程缺失 | 易出现证书过期、链不完整、部署来源不明及轮换中断 |

仅替换一张公开 CA 证书不能解决这些问题：必须同步修复客户端验证逻辑，并核实线上实际部署。

## 4. 目标证书体系

### 4.1 公网节点

优先使用稳定的受控域名，为域名申请公开 CA 签发的服务端证书。建立自动申请和续期流程，并记录域名验证方式、签发机构、证书资产和负责人员。

服务端发送“叶子证书 → 必需的中间证书”，客户端以受信任根为锚完成验证。根证书通常不需要随服务端链发送。连接地址可以是 IP，但用于验证的 `serverName` 必须与证书 SAN 匹配；如果直接验证 IP，证书必须包含对应的 IP SAN。

### 4.2 私有部署

私有 CA 的最小规范结构可以是：

```text
客户端预置信任的根 CA
  └─ 服务端叶子证书（CA=false，包含准确 SAN 和 serverAuth 用途）
```

规模扩大后可以引入中间签发 CA。根 CA 私钥离线或存放于受控签名设施，服务端只持有本节点的叶子私钥及公开证书链。每个节点独立密钥，测试与生产使用不同信任根。客户端只能导入公开信任材料。

## 5. 实施与迁移步骤

1. **盘点线上状态**：逐节点记录协议、TLS 开关、连接地址、验证名称、实际发送的证书链、有效期、客户端信任来源和当前客户端版本。HTTP/3 必须使用支持 QUIC 的实际客户端检查，不能用 TCP TLS 检查结果代替。
2. **准备规范证书**：生成独立叶子密钥，签发用途和 SAN 正确的叶子证书，准备按顺序排列的中间证书链，验证证书与私钥匹配。不得继续把 CA 私钥放在节点上充当服务端密钥。
3. **修复客户端验证**：Java HTTP/2 移除不安全信任管理器并明确启用名称验证；Rust HTTP/2 使用标准证书验证器和握手签名验证；Rust HTTP/3 删除按 DER 相同无条件放行的回退。保留私有 CA 导入能力，但统一走标准路径验证。
4. **处理信任分发**：公共 CA 路线使用所选客户端信任库；私有 CA 路线提前通过可信更新渠道分发新根。明确自定义 CA 是替代还是补充公共根，避免各端语义不一致。可选 SPKI 绑定应作为标准验证通过后的附加限制，并准备轮换备用指纹。
5. **协调切换**：严格客户端不能直接切向仍使用旧 CA 叶子的服务端。需要时建立独立的新端口或节点，先部署有效证书并验证，再发布严格客户端和新配置，灰度迁移后关闭旧入口。重叠信任只允许仍有效且符合策略的新旧证书，不恢复验证绕过。
6. **明确失败行为**：过期、未知 CA、名称错误、签名错误或证书链不完整时拒绝连接并给出可定位的错误；不静默降级到明文或无校验 TLS。回滚使用仍有效的证书和经过验证的客户端版本。

整改期间应检查内置信任与导入功能的所有调用方，避免只修复默认节点而遗漏其他配置入口。

## 6. 生产运行措施

- **私钥管理**：私钥通过部署密钥系统或受控文件挂载提供，设置最小读取权限，不进入仓库、镜像、日志或客户端安装包。若发现曾泄露，立即更换密钥并执行相应撤销或信任移除流程。
- **自动续期与加载**：续期后检查新证书链、SAN、用途、有效期和密钥匹配，原子替换文件；验证热加载是否真正生效，不支持热加载时采用滚动重启。观测新建连接出示的证书，而非只检查磁盘文件。
- **到期预警**：监控证书剩余有效期、续期失败、握手失败率和客户端版本分布。告警阈值根据证书寿命设定，例如在剩余寿命的 1/3 和 1/6 时预警，短期证书不照搬固定 30 天阈值。
- **轮换与应急**：制定私钥泄露、CA 变更、证书误签及节点下线的操作流程。对绑定证书或公钥的客户端，必须具备可信的远程配置或版本更新途径来撤销旧信任；不能只依赖证书过期。
- **协议策略**：HTTP/3 使用 TLS 1.3；HTTP/2 明确允许的 TLS 版本与算法。生产配置拒绝意外的明文入口及不安全验证开关。
- **可追溯性**：记录证书序列号、公开指纹、签发来源、部署时间、节点和负责人；日志禁止记录私钥。固定的公共根集合随客户端依赖更新，纳入维护计划。

## 7. 生产上线验收条件

本节是未来整改必须执行的验证计划；本次文档变更没有执行这些测试，也没有部署证书。

| 验收项 | 通过条件 |
| --- | --- |
| 各端正常连接 | Java、桌面端和 Android 的目标协议路径均能用有效证书连接，名称及 SAN 匹配 |
| 非法证书拒绝 | 过期、尚未生效、未知 CA、错误 SAN、CA 充当叶子、缺少必要中间证书、错误签名均被拒绝 |
| 中间人防护 | 替换为攻击者自签或其他名称的证书时不能连接，不能自动退回不安全路径 |
| 私有 CA | 仅信任授权的 CA，标准链验证和名称验证生效；导入公开证书不会启用通用验证绕过 |
| 公钥绑定 | 配置绑定时必须同时通过标准验证；错误绑定拒绝连接，计划内轮换可完成 |
| 续期演练 | 新证书加载到新连接，无需重新打包内置叶子证书；连接影响满足发布要求 |
| 信任撤销 | 泄露密钥及旧信任可以在约定时限内退出，旧证书无法通过兼容回退继续使用 |
| 部署一致性 | 对线上实际 HTTP/2、HTTP/3 握手检查，而非仅验证本地 PEM；磁盘与运行状态一致 |
| 运维准备 | 有责任人、告警、轮换记录、应急流程以及不会重新关闭验证的回滚方案 |

生产发布前必须关闭上述 P0 问题，完成证书替换和实际握手验收。本文仅覆盖 TLS 方面的上线门槛；应用层加密、认证授权、密钥管理和其他生产安全要求仍需独立审查。
