# Windows TUN 断网重连恢复及验证

## 行为

Windows TUN 运行时使用一个常驻 PowerShell 子进程，每 3 秒检查物理 IPv4 默认出口的接口、源地址、网关、真实 DNS 和 FakeDNS 接管状态。忽略 TUN 默认路由、无效地址和已断开的接口。连续两次观测到同一新状态才恢复；连续离线后回到原地址也恢复。短暂 DHCP 空窗不触发反复重建。

恢复在原有管理员进程内执行，不重新申请 UAC：停止并等待旧协议栈和连接调度任务退出、取消其所有转发任务、恢复旧 DNS 并精确删除所拥有的路由，然后重新发现出口、创建 TUN、配置绕过路由和 DNS。初始化失败保留进程并继续重试；停止文件和退出信号仍有效。首次启动的 DHCP 等待与报错行为保持原有约定。

FakeDNS 引擎跨会话保留，浏览器缓存的 FakeIP 仍能反查原域名。旧 TCP 连接会关闭，需要应用重试，不提供无缝迁移。

新绕过路由生效后，TUN 原子替换 `proxy-java.yml.network-reset` 中的代际标记。代理核心的现有配置观察器检测标记，串行关闭旧节点连接并按现有手动/自动策略重新建连；旧代际的迟到连接不能重新加入。手动模式重建失败也使用现有节点熔断退避重试，保留证书错误阻断。标记不修改节点配置，也不开放控制端口。

桌面生成的 TUN 配置显式指定 `proxy_reconnect_file`；旧桌面生成的 `tun-nodes.toml` 使用同目录兼容路径。独立配置可显式指定该字段。当前自动网络检测仅适用于 Windows。

## 路由清理

Windows 退出时保留 DHCP 当前的默认路由，不再重新添加启动时捕获的旧网关。删除自建路由限定目标、掩码和下一跳；精确的既有路由可复用但不记为本进程所有，添加失败不再假报成功。默认网关和 DNS 接口查询排除 FakeIP 网关，并按接口与路由的合计度量排序。

## 本机真实链路验证

使用独立端口 1088 的代理核心和临时 `SimplePlaneRecoveryTest` Wintun，保留原客户端进程及配置。测试核心连接 Azure HTTP/3 节点；两轮把物理 WLAN 的有效 DNS 从 `198.18.0.2` 重置为 DHCP DNS，模拟重连时的 DNS 覆盖。

- 两轮均由原 TUN PID `33796` 自动重建，未新建管理员进程。
- 第一轮恢复路由时间为 UTC `06:18:17.769`，代理 QUIC 握手为 `06:18:18.429`；第二轮分别为 `06:19:18.643`、`06:19:19.408`。从 DNS 重置到代理握手分别为 20.569 秒、19.913 秒。
- 恢复前及两轮恢复后，`cn.bing.com` 返回 HTTP 301，`www.baidu.com`、`www.bing.com` 返回 HTTP 200。恢复后请求耗时约 0.33–0.71 秒。
- 三个域名的 FakeIP 在两轮恢复前后保持一致。
- 优雅退出后有效 DNS 恢复 `202.118.66.6`，仅保留物理默认路由 `172.16.40.1`，无 TUN `/1` 路由或监控子进程残留。测试核心已清理。

本机测试没有关闭真实 WLAN，也没有实际切换热点。断线及 IP/网关变化由自动测试的 OS 查询替身覆盖；上述实际耗时来自真实 Windows DNS 变化后的完整 TUN/代理重建链路。

本次构建的两个组件已更新到 `E:/SimplePlane/resources` 和工作区桌面资源目录，原组件保留带时间戳的备份。客户端已重新连接其已保存的系统代理配置；新代理进程 PID `32284`，节点可用，Bing 实际 SOCKS5 HTTPS 请求返回 200。TUN 自动恢复在之后开启 TUN 时使用。GitHub 上先前的 0.3.1 产物尚未重新构建。

本机诊断证据位于忽略目录 `.build/network-recovery-live/`；Java 和 Rust 测试结果分别位于 `.build/network-recovery-java-tests.log`、`.build/network-recovery-rust-tests.log`。临时测试用凭据配置不会作为产物或提交内容发布。
