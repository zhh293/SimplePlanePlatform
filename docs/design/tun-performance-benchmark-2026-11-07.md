# TUN 性能实测：Windows 真实链路与 WSL 隔离基线

测试日期：2026-11-07。结论针对本次环境和采样窗口，不作为网卡、系统或代理的通用性能上限。

## 结论

1. 本次 Windows 下载中，没有观察到 TUN 进程 CPU 饱和。真实链路、绕过代理的直连和 SOCKS5 都处于几十 Mbps；现有证据更指向公网/代理传输链路限制，不能证明 Windows TUN 的逐包 I/O 是当前主要瓶颈。
2. TUN 有可测量的开销。4 MiB 测试中，四并发的吞吐中位数从 SOCKS5 的 36.91 Mbps 降到 TUN 的 34.60 Mbps；单连接从 28.63 降到 22.17 Mbps。但波动较大，不能把这两个差值当成固定损耗率。
3. 当前源码 release 版本在 WSL Linux 隔离环境中，TUN 下载约 4.9–5.0 Gbps，上传约 1.5–1.7 Gbps；TUN 进程消耗约 1.1–1.4 个 CPU 核心。下载从单连接增加到四连接几乎不增长，符合集中事件循环限制吞吐的特征，但没有函数级采样，尚不能量化复制、分配、系统调用各占多少。
4. 16 MiB 测试中的两组 SOCKS5 四并发均未完整通过：一组出现提前 EOF，一组出现接收超时。这两组没有经过 TUN，不能归因于 TUN。应优先检查代理传输的数据完整性、流关闭及排队/背压，再讨论进一步提高吞吐。

## Windows 测试方法

- 复用正在运行的 TUN PID 31664 和 Java PID 27688，不重启客户端、不切换节点、不修改 Windows 默认路由、DNS 或代理配置。
- 实际选中的节点是 `20.78.53.111:9090`，传输为 HTTP/3，`connectionsPerNode=1`。用户提供的 AWS 节点 `54.172.101.190` 已验证 SSH 可用，但本次 Windows 对照使用当前选中的节点。
- 在当前节点现有 Nginx 的 `/var/www/html` 临时创建随机文件名的测试文件，内容均为字节 `Z`，分别为 4 MiB 和 16 MiB。没有修改 Nginx 配置；Linux 文件页缓存参与服务，客户端数据仅在内存校验后丢弃。
- SOCKS5 客户端绑定源地址 `127.0.0.2`，与 TUN 适配器的路由约定一致，确保目标流量通过远端代理。
- TUN 路径显式向 `198.18.0.2:53` 查询目标名称 `20.78.53.111`，获得 FakeIP 后连接该 FakeIP，避免节点公网 IP 的 bypass 路由使测试绕开 TUN。
- 直连基线直接连接节点公网 IP 的 80 端口，利用现有节点 bypass 路由绕过 TUN 与本地代理。
- 4 MiB 测试执行四轮，顺序为 SOCKS/TUN、TUN/SOCKS、SOCKS/TUN、TUN/SOCKS；每种路径分别测单连接、四并发。
- 16 MiB 持续下载执行两轮反向顺序，并补单连接和四并发直连各一组。失败组单独保留，不参与吞吐统计。
- 吞吐按完整有效载荷字节数除以整组墙钟耗时计算，包含连接建立和 HTTP 请求。CPU 为进程 CPU 时间增量除以墙钟耗时，单位为“占用的 CPU 核心数”，并非整机 CPU 百分比。
- 首字节延迟单独用一字节 Range 请求测量，计入完整代理建连。TUN 的本地 TCP 握手完成时间不等于远端连接完成时间，因此不拿两种路径的 `setup_ms` 直接比较。

### 4 MiB：吞吐中位数

每行四组样本；四并发列为总吞吐。

| 路径 | 单连接 Mbps | 四并发 Mbps |
| --- | ---: | ---: |
| SOCKS5 | 28.63 | 36.91 |
| Windows TUN → SOCKS5 | 22.17 | 34.60 |

单连接样本范围：SOCKS5 9.43–31.19 Mbps，TUN 7.91–30.71 Mbps。四并发样本范围：SOCKS5 16.29–38.71 Mbps，TUN 21.82–36.17 Mbps。首轮偏低，以上统计没有事后删除该轮。

一字节响应首字节延迟中位数：SOCKS5 322.50 ms，TUN 311.29 ms，每条路径 12 次。差异小于本次网络波动，不能据此认定 TUN 降低了远端延迟。

### 16 MiB：持续下载

| 路径 | 单连接 Mbps | 四并发 Mbps | 有效组数 |
| --- | ---: | ---: | --- |
| 直连公网 HTTP | 40.71 | 32.91 | 每种并发各一组 |
| SOCKS5 | 29.65 | 无有效结果 | 单连接两组；四并发两组失败 |
| Windows TUN → SOCKS5 | 23.56 | 33.36 | 每种并发各两组 |

SOCKS5 单连接两次分别为 20.78、38.51 Mbps，TUN 单连接分别为 24.81、22.32 Mbps；TUN 四并发分别为 29.77、36.94 Mbps。小样本和链路波动使其不适合推导固定性能差值。

失败详情：

- 第一组 SOCKS5 四并发中，至少一条请求只收到 `16,336,385 / 16,777,216` 字节便提前 EOF，缺少 440,831 字节。
- 第二组 SOCKS5 四并发中，至少一条请求触发 20 秒接收超时。不能据此断言其他三条请求也失败，也不将组级失败数当作单请求失败率。
- Nginx 访问日志记录本次全部 105 次请求。服务端针对测试文件记录了完整 HTTP 206 响应；访问日志的发送字节数不能证明最终客户端已收到数据。根因仍可能位于后续转发、连接关闭或网络路径，尚未锁定具体模块。

### CPU 与内存

- 4 MiB TUN 测试：单连接平均约 0.023 核，四并发平均约 0.052 核。
- 16 MiB TUN 测试：单连接平均约 0.030 核，四并发平均约 0.087 核，最高一组约 0.103 核。
- 本机 Java 在有效代理下载组中约占 0.08–0.19 核。测量期间存在用户其他业务流量，进程统计不是测试流量的独占成本。
- 远端代理取得 66 个约一秒间隔的有效 CPU 样本，覆盖约 65 秒：平均约 0.112 核，最高单间隔约 0.669 核，没有在该窗口观察到进程 CPU 饱和。遥测 SSH 后续停止接收数据，已结束本次采样连接；不能声称覆盖了全部测试阶段。
- Windows 测试中的一个内存快照：TUN 工作集约 112.4 MiB、私有内存约 146.5 MiB；Java 工作集约 166.4 MiB、私有内存约 436.1 MiB。这是含其他业务流量的时点快照，不是峰值或内存泄漏结论。

## WSL：排除公网的本地适配器测试

从当前 `tun-adapter` 源码离线构建 release 版本，执行时把二进制和测试脚本复制到 WSL `/tmp/sp-tun-perf-20261107`。压测数据不写磁盘、不经过 `/mnt/e`；最终只将小型 JSON 和日志回存到工作区。

在 `unshare -n` 创建的独立网络命名空间里启动 Linux TUN、内存数据服务和一个 Python SOCKS5 转发服务，MTU 1500，`RUST_LOG=warn`。同一个 SOCKS5 服务同时用于基线和 TUN 路径，不包含 Java 或远端 QUIC。测试结束退出命名空间并结束所有临时进程。

每个组合测两轮，每次传输约四秒，SOCKS/TUN 顺序交替。下载逐块校验内容；上传由服务端核对内容和收到的总字节数。16 组吞吐样本及延迟探测均完成，没有记录数据校验失败。

| 路径 | 单连接下载 Gbps | 四连接下载 Gbps | 单连接上传 Gbps | 四连接上传 Gbps |
| --- | ---: | ---: | ---: | ---: |
| 本地 SOCKS5 | 15.50 | 7.71 | 15.89 | 7.35 |
| Linux TUN → 本地 SOCKS5 | 4.90 | 5.02 | 1.52 | 1.69 |

本地 SOCKS5 服务和客户端由 Python 实现，四并发基线本身会受运行时与调度影响，不能把这些数字当成操作系统的网络极限。TUN 进程消耗约 1.1–1.4 核，较高负载下的集中事件循环值得后续剖析。

本地完整建连加四字节回显的延迟中位数：SOCKS5 0.555 ms，TUN 0.795 ms，每种路径十次。它反映本地完整路径的额外延迟，不是单独 SOCKS5 握手的耗时。

Linux 使用 tun2 的 Linux TUN 后端，Windows 使用 Wintun，且生产日志级别不同。以上 Gbps 数值不能外推为 Windows Wintun 的吞吐上限，也不能证明 Windows 的每种 I/O 场景都表现相同。

## 下一步判断

现有数据支持先检查代理链路完整性与公网/QUIC 传输表现。若后续需要追求本地千兆以上吞吐，再针对当前集中事件循环做函数级采样，量化逐包读写、缓冲复制、分配和连接扫描成本。目前未修改生产源码，也没有基于猜测改变 TCP 缓冲或协议栈。

本次仅测 Windows 下载；Windows 上传和 Wintun 的本地饱和测试尚未测量。WSL 上传不能替代这两个指标。
