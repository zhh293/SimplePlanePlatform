# Windows 桌面 TUN 间歇断连排查（2026-10-30）

用户现象：桌面安装版，使用一段时间后网页无法打开，但界面仍显示连接。

结论：源码中确认了状态误报、socket 未释放、双向转发丢数据、单方向超时四类缺陷。它们都位于桌面 TUN 的实际调用路径；其中数据丢失和超时可以影响单条连接，socket 累积更符合长时间运行后整体恶化。没有故障时刻的 TUN 日志，尚不能将用户那一次故障归因到其中某一个缺陷。不是已完成现场根因闭环，也未修复或替换安装包。

## 1. 桌面端会保持错误的“运行中”状态

源码位置：

- `desktop/src-tauri/src/commands.rs:108`：`status()` 只核对 Java 代理端口和进程，直接返回缓存的 `tun_status`，不复查 TUN。
- `desktop/src-tauri/src/process.rs:668`：UAC 启动拿到实际进程句柄后立即 `CloseHandle`，随后返回一个运行约 30 秒的 `cmd.exe` 占位进程。这不是 TUN 进程，不能用其退出码判断 TUN 存活。
- `desktop/src-tauri/src/process.rs:398`：Windows 网卡检测硬编码名称 `SimplePlane`。
- `tun-adapter/src/tun_device.rs:46`：创建配置没有调用 `.tun_name(...)`；本地锁定依赖 `tun2 4.0.0` 的 Windows 实现会回退到名称 `wintun`。因此默认创建名称与桌面检测名称不一致。
- `desktop/src-tauri/src/process.rs:520`：启动检查 5 秒后找不到接口，仍设为 Running。

这些问题能解释为什么“连接”标记不能代表网络可用；但状态误报本身不是数据面断开的原因。

修复方向：保存真实提升权限进程的句柄/PID，通过可验证的就绪信号确认启动；持续检测实际进程与数据面健康；取消检测失败后假定成功；统一实际网卡名称。不能直接用现有 `tun_process.try_wait()` 增加运行期检测，否则会把占位进程约 30 秒后的正常退出误判为 TUN 退出。

## 2. SocketSet 永久保留已结束的连接

源码位置：`tun-adapter/src/stack.rs:185`、`:368`、`:404`、`:505`。

每个 TCP socket 分配 64 KiB 接收缓冲和 64 KiB 发送缓冲。清理只从 `pending_handles`、`active_connections`、`listening_ports` 移除追踪项，整个文件没有调用 `sockets.remove(handle)`。SocketSet 仍拥有 socket 和两块缓冲。

隔离复现：建立含 1,000 个 Closed socket 的集合，执行相同的 pending retain 清理。追踪项为 0，但集合仍有 1,000 个 socket，仅收发缓冲就占 125 MiB。实际泄漏速率取决于累计创建连接数，不能从该测试推算用户机器多久断网。

潜在后果：内存持续增长，协议栈轮询对象增多；被从追踪表移除但未关闭的 socket 还可能干扰后续流量。不能依据这项测试宣称现场已发生 OOM。

修复方向：统一管理 socket 生命周期，失败握手需要 abort 并移除；正常关闭要继续驱动 FIN/ACK 和必要的接收，进入终态后释放。不能在 `socket.close()` 后立即无条件 remove，以免截断尚未发出的数据与 FIN。

## 3. 背压处理会丢失已经进入 TCP 字节流的数据

源码位置：`tun-adapter/src/stack.rs:418`、`:423`、`:440`。

### 上传方向

先 `socket.recv_slice()` 消费数据，再 `conn.tx.try_send()`。如果 channel 满，直接忽略错误里携带的数据并 break，没有重试缓存。

隔离复现：队列满时读取了 7 字节，入队失败；TCP 接收缓冲已空，数据没有被保留。这不是可依赖 TCP 重传恢复的普通网络丢包：数据已由用户态 TCP 栈接收，再由应用桥接层丢弃。

### 下载方向

`socket.can_send()` 只表示存在可写空间，不代表整个数据块都能写入。`send_slice()` 返回实际写入长度，当前代码仅打印该值，然后丢弃整个原始数据块。

隔离复现：64 KiB 缓冲只剩 1 字节，`can_send()` 为 true；写入 32,768 字节只接受 1 字节，剩余 32,767 字节在当前调用逻辑中没有保留。

潜在后果：TLS/HTTP 内容损坏、请求卡住或连接关闭，容易在下载、上传、高并发或接收端变慢时暴露。两项测试使用实际锁定的 smoltcp API，重现源码中对应操作顺序；不是整机 Wintun 压测。

修复方向：向队列发送前预留容量，或保留未发送块；对部分写入维护偏移并重试，保证数据顺序与关闭顺序。单纯扩大缓冲区只能推迟触发。

## 4. 单方向 120 秒超时误伤仍在传输的连接

源码位置：`tun-adapter/src/socks5.rs:70`、`:110`、`:99`、`:139`。

两个方向分别对 read 设置 120 秒超时，超时后 shutdown 对端写方向。上传方向没有应用数据，不等于下载方向空闲；TCP ACK 在协议栈处理，不会作为上传应用数据刷新这个计时器。

隔离复现直接调用当前生产代码 `proxy_tcp_stream()`，通过 localhost mock SOCKS5 服务和 Tokio 虚拟时间，在 0、30、60、90 秒持续下发数据。超过 120 秒，服务端仍观察到客户端上传方向 EOF。测试确认了错误的半关闭；服务端是否随即停止下载取决于对端实现，不声称所有下载都会恰好在两分钟终止。

修复方向：明确连接级空闲策略，按双向活动更新；正确处理 EOF、错误、半关闭和任务取消。不能用无限等待掩盖生命周期泄漏，也不能任意一侧 EOF 就截断另一侧尚未传完的数据。

## 5. 其他条件性风险

- `tun-adapter/src/route_guard.rs:207`：只在启动时读取默认网关并写 bypass 路由，没有网络切换/唤醒后的路由刷新。若故障与切 Wi-Fi、VPN、睡眠唤醒相关，应检查断线时实际路由；目前用户未确认这个触发条件。
- `tun-adapter/src/stack.rs:165`、`:593`、`:676`：在唯一协议栈循环里 await 内网 DNS 请求，每个超时可停顿约 3 秒；连续查询可能累积停顿。本机运行配置没有显式 intranet_dns，不把它列为本次首要原因。
- `tun-adapter/src/main.rs:382`：健康检查只完成本地 SOCKS5 认证，不证明远端节点或互联网可达；所谓 Direct 降级最终仍经相同 SOCKS5，不能提供真实的故障旁路。

## 6. 本机观测与证据边界

- 排查时存在 `E:\SimplePlane\simple-plane-desktop.exe` 和安装目录内 Java 进程，没有观察到 `tun-adapter` 进程。这个快照不能证明故障时 TUN 崩溃：用户也可能已切回系统代理。
- `E:\SimplePlane\logs\proxy-local.log` 中有实际 QUIC 断开、重连成功和更早的重连超时。例如当天 14:50:40、14:53:55、17:24:56、19:22:10 的断开随后约 0.6–0.7 秒重连成功。该日志不能单独证明 TUN 导致断开，也不能用“重连成功”推断所有旧业务连接都恢复。
- 本机 `tun-nodes.toml` 没有配置 `[log].file`；默认值为空。UAC 路径隐藏窗口且未接管真正 TUN 的 stdout/stderr，没有找到能关联故障时刻的 TUN 文件日志。
- 已安装的 `tun-adapter.exe` 与仓库 resources 下二进制大小、修改时间不同。以上代码结论针对当前源码，尚未证明安装二进制与当前源码完全一致。

## 7. 验证产物与下一步

隔离验证代码：`.build/tun-disconnect-audit/src/lib.rs`；独立 Cargo 项目，不修改生产源码，不创建 TUN，不改系统路由/DNS，不重启现有客户端。仅使用 localhost mock 网络和内存协议栈。

执行：`cargo test --manifest-path .build/tun-disconnect-audit/Cargo.toml --offline audit_ -- --nocapture`，使用仓库本地 Rust/MSVC 工具链。

结果：4 passed / 0 failed。这里“passed”表示断言成功证实了缺陷，不表示修复已完成。smoltcp 0.11.0、Tokio 1.52.3 与生产 Cargo.lock 一致。

修复顺序建议：

1. 补齐真实进程监管、启动就绪判断、退出原因和可轮转的文件日志，解决假连接并能捕获下一次故障。避免日志包含密钥。
2. 修复数据桥接的背压与部分写入，增加双向完整性测试。
3. 修复 socket 生命周期，增加大量短连接、FIN/RST/超时后的资源回收验证。
4. 修复双向空闲与半关闭语义，验证持续下载/上传超过两分钟。
5. 使用新构建在 Windows 做长时间 TUN 实测，再验证网络切换与睡眠唤醒；不能用单元复现替代该验收。

要锁定用户那一次故障，还需将断线时间、TUN 退出/存活状态、内存与 socket 数、远端连接错误和当时的路由对应起来。现有证据足以确认需修复的缺陷，但不足以指定唯一现场根因。
